# Benchmarks

This documents how the fixed-commit pilot corpus is built, how candidates are
labelled and scored, and the current numbers. The labels themselves are the
source of truth and live in `benchmarks/labels/`; this file explains how to read
them.

## Corpus

Six small, popular Python projects, each pinned to a fixed commit in
`benchmarks/manifest.json`:

| project | labels |
|---|---:|
| click | 72 |
| httpx | 76 |
| pytest | 259 |
| requests | 42 |
| starlette | 46 |
| werkzeug | 123 |
| **total** | **618** |

The harness clones the declared commits, runs a read-only `code` profile, and
writes one JSON result plus logs per project:

```powershell
python benchmarks\run_benchmarks.py `
  --workspace C:\Temp\auto-code-audit-benchmarks `
  --output C:\Temp\auto-code-audit-benchmarks\results.json
```

Use `--project requests` for one entry, `--refresh` to replace a checkout at the
wrong commit, `--dry-run` to validate without network. The harness never
installs or executes target-project code. Consecutive runs against the same
`--json` path diff against the previous report (`previous_run` block + "Changes
since last run"), so a review session starts from what changed.

## Labels and ground truth

`benchmarks/labels/<project>.json` holds human adjudications keyed by the stable
`(scanner, target_id)` signature. Each label is `true_finding` or
`false_positive` with a reason, and carries provenance (`human_verified`,
`reviewers`, `ground_truth_version`). True findings may carry an `issue_id` so
several candidates reporting one defect collapse to a single issue.

Of the 618 committed labels, 594 still match a candidate at the pinned commits;
24 are stale — their target disappeared after scanner changes (all false
positives, e.g. `@overload` signature-stub clusters and pre-filter
`__init__`-boilerplate regions). Stale labels surface as `unmatched_labels` so
label drift stays visible rather than silent.

`benchmarks/gold_manifest.json` is a deterministic curated subset used as the
trust anchor for scoring an AI adjudicator: 100 entries (all 16 true findings
plus 84 false positives, 20 tagged `boundary`), regenerated by
`benchmarks/gold_sample.py` and pinned by an integrity test.

## Metrics

- **precision** — confirmed findings / labelled candidates (matched subset).
- **coverage** — labelled vs. total candidates per project, so unlabelled
  channels stay visible.
- **review_burden** — candidates per confirmed finding.
- **unique_issues** — distinct defects behind the true findings (via `issue_id`).
- **unique_issue_ratio** — `unique_issues / true_findings`: how far the findings
  collapse into distinct defects (corpus 0.62).
- **evidence_per_issue** — `true_findings / unique_issues`: average labelled
  candidates corroborating each defect (corpus 1.6).
- **candidates_per_kloc** / **runtime_per_kloc** — pass cost vs. package size.

## Expected-value cohorts

`run_all.value_cohort` ranks every candidate into a `high` / `medium` / `low`
cohort from label-independent evidence: near-exact duplicates and region twins
are high; plain shared-capability regions are medium; everything else is low.

| cohort | candidates | true findings | precision |
|---|---:|---:|---:|
| high | 69 | 12 | 0.17 |
| medium | 21 | 2 | 0.10 |
| low | 504 | 2 | 0.004 |

The default worksheet hides the low cohort — the ~90 high/medium candidates
carry 14 of the 16 confirmed findings.

## Evidence fusion

`benchmarks/evidence_fusion.py` quantifies adjudicating *issues* instead of
candidates. The **proposed** (predictive, label-independent) view merges two
clusters from different channels into one issue only when their member-symbol
sets are identical; everything else is its own bundle. The **retrospective**
view merges by the `issue_id` assigned during adjudication. Both are printed
side by side so the distinction stays visible. At the pinned commits the
proposed view collapses 594 candidates into 574 bundles (corroborated-bundle
precision 28.6%, single-bundle 1.4%, issue recall 0.8, fusion purity 1.0).

## Mutation corpus

`benchmarks/mutation/project/` is a synthetic fixture injecting one known defect
per channel (dead module, duplicated function, env write without a read,
`strict=False` loosening, hardcoded path, capability overlap, region mutants).
`run_mutation.py` compares detected `(scanner, target_id)` signatures against
`benchmarks/mutation/expected.json`; recall is exact target matching, not count
matching. Current corpus: 25 injected targets, 25 matched, recall 1.000. The
runner exits nonzero on any miss, so the regression gate covers scanner recall
as well as corpus precision.

## External probe: arrow (not part of the labelled corpus)

One-off validation against an unlabelled, mid-size pure-Python project to
check the tool on unfamiliar code (no prior expectations):

| project | scan time | dead | hardcoded | style | dup clusters | regions | forks |
|---|---:|---:|---:|---:|---:|---:|---:|
| arrow (arrow-py, pinned HEAD 2224255) | 1.08s | 0 | 0 | 0 | 8 | 6 | 0 (+4 small) |

Notable candidates (all map to real smells in that codebase): 9 locale
`_format_timeframe` methods at 0.84-1.00 edge similarity, 4 `describe`
twins, `api.get` vs `ArrowFactory.get` near-duplicates, and internal
repetition inside `DateTimeParser.parse` (L14/L15/L16). Full worksheet in
the external state directory; command was the standard read-only code profile:

``powershell
python run_all.py --root <arrow-checkout> --package arrow --profile code 
  --no-doc-channel --all-py --state-dir <external-state> --read-only 
  --json <state>\latest.json --markdown <state>\latest.md
``
